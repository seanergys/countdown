# Contributing to COUNTDOWN SEANERGYS

This guide explains how to propose changes, how commit messages become the
changelog, and how releases are made. For build and test instructions, see
[BUILD INSTRUCTIONS](README.md#build-instructions) and
[Baseline MPI tests](README.md#baseline-mpi-tests) in the README.

## Workflow

1. Open or pick a GitLab issue.
2. Create the branch from the issue page ("Create merge request"). GitLab names
   the branch after the issue and links the two.
3. Push your commits and open a merge request (MR) against `main`.
4. Before you request a review, give the MR a Conventional title (see below).
5. After approval, merge with squash (the default). The MR title becomes the
   single commit on `main`.

Direct pushes to `main` are possible for maintainers but should stay
exceptional. Use an MR for code changes and releases.

## MR titles

With squash, `main` receives one commit per MR, and its message is the MR title.
The changelog is generated from the messages of the commits on `main`, so the
title must follow [Conventional Commits](https://www.conventionalcommits.org):

```text
<type>(<scope>): <description>
```

Example: `feat(access-daemon): move EasyBUS calls to the AD worker`

- Write the description in the imperative mood and lower case, without a final
  period.
- Describe the change for a user of COUNTDOWN, not the implementation steps.
- With squash, commit messages inside the branch are free-form: only the MR
  title reaches `main`. If you merge without squash, or push directly to `main`,
  every commit reaches the changelog, so every commit message must be
  Conventional.

### Types

| Type       | Use for                               | Changelog section |
| ---------- | ------------------------------------- | ----------------- |
| `feat`     | New functionality                     | Added             |
| `fix`      | Bug fixes                             | Fixed             |
| `refactor` | Code changes with no behaviour change | Changed           |
| `perf`     | Performance improvements              | Changed           |
| `docs`     | Documentation                         | Changed           |
| `test`     | Tests                                 | Changed           |
| `build`    | CMake, dependencies, packaging        | Not listed        |
| `ci`       | GitLab CI configuration               | Not listed        |
| `chore`    | Maintenance with no user impact       | Not listed        |
| `style`    | Formatting only                       | Not listed        |

The type decides the section: `fix(access-daemon): remove a stale cache` is
listed under Fixed. The Removed and Deprecated sections are for features that
users lose: use a breaking `feat!` or `refactor!` title for removals, and
mention deprecations in the description of the MR that introduces them.

### Scopes

The scope is optional. Use one of these names when it applies:

| Scope           | Area                                 |
| --------------- | ------------------------------------ |
| `access-daemon` | Access Daemon backend and EasyBUS    |
| `mpi`           | MPI interception and instrumentation |
| `build`         | CMake and build options              |

Add new scopes to this table in the same MR that first uses them. Older commits
use `ad`; `cliff.toml` rewrites it to `access-daemon`.

### Breaking changes

A change is breaking when existing users must change something: a build option,
an environment variable, an output format, or a removed feature.

Mark it with `!` after the type or scope, and describe the migration in a
`BREAKING CHANGE:` footer of the MR description:

```text
feat(access-daemon)!: require the Access Daemon domain in the configuration
```

Breaking changes appear in the Breaking section, whatever their type.

## Changelog

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and is generated by [git-cliff](https://git-cliff.org) from `cliff.toml`.

- Do not edit `CHANGELOG.md` in feature MRs: the entry for an MR is generated
  from its commit on `main`, which exists only after the merge.
- `CHANGELOG.md` changes in two kinds of MR:
  - release MRs (see [Releases](#releases));
  - changelog updates, which refresh the Unreleased section without a new
    version.
- To preview the unreleased changes locally:

  ```sh
  git cliff --unreleased
  ```

### Updating the Unreleased section

Do this when merged changes should be visible in `CHANGELOG.md` before the next
release:

1. Create a branch from an up-to-date `main`.
2. Regenerate the changelog:

   ```sh
   git cliff -o CHANGELOG.md
   ```

3. Open an MR titled `chore(changelog): update unreleased` and merge it. The
   `chore` type keeps this commit out of the changelog.

- To fix how an old commit is classified, add a `sha` rule to `commit_parsers`
  in `cliff.toml`. Do not edit `CHANGELOG.md` by hand: every release regenerates
  the whole file from the git history.

The fork point from upstream COUNTDOWN is tagged `upstream-2.0`. `cliff.toml`
skips that tag, so upstream history does not appear in the changelog.

## Versioning

The project follows [Semantic Versioning](https://semver.org). The version is
chosen at release time, not per MR:

- **Major**: at least one breaking change.
- **Minor**: new functionality, no breaking changes.
- **Patch**: fixes only.

`git cliff --bumped-version` suggests the next version from the commit types.
The maintainer confirms it.

## Releases

1. Create a branch from an up-to-date `main`, for example `release-v2.1.0`.
2. Set the version in `project(... VERSION ...)` in `CMakeLists.txt`.
3. Regenerate the changelog:

   ```sh
   git cliff --tag v2.1.0 -o CHANGELOG.md
   ```

4. Review `CHANGELOG.md`, then open an MR titled `chore(release): v2.1.0`.
5. After the merge, tag the commit that the MR created on `main`, and push the
   tag. Do not tag the release branch: with squash, its commits never reach
   `main`.

   ```sh
   git switch main && git pull
   git tag -a v2.1.0 -m "COUNTDOWN SEANERGYS v2.1.0"
   git push origin v2.1.0
   ```

6. Create the GitLab release from the tag and paste the version's changelog
   section as its description.
